# 哨兵模式（Sentry Mode）

锁车后车辆保持**监控/警戒**（摄像头录制、周界监控等）的低功耗状态。

## 与 [[STR]] 的本质区别（互斥，非叠加）
| | 哨兵模式 | [[STR]] |
|---|---|---|
| 主 SoC | **保持唤醒**（要算力跑监控） | **断电冻结** |
| 手段 | 电源**策略** `gua_policy_sentinel_enter` 关屏/音频 | 电源**状态** SUSPEND，全冻 |
| process | 监控 process 继续运行 | 全部 frozen，停摆 |

> 要哨兵监控就**不能进 STR**；进了 STR 哨兵也一起冻。锁车后走哪条由业务决定，二者不并存。

## 常见误区：休眠时还能哨兵监控吗？
不能，也不会发生。锁车瞬间系统按"要不要监控"**分岔二选一**：
- 开哨兵 → **根本不进 STR**，SoC 一直醒着跑监控（只关屏/音频省一点电）。
- 没开哨兵 → 才进 [[STR]] 深睡，全冻结。

**耗电换监控**（物理互斥）：STR 几乎 0 耗电但全瞎；哨兵很费电（类比特斯拉哨兵约 1 英里续航/小时）但摄像头全程盯着。不可能既"CPU 断电极省电"又"CPU 跑算法监控"。

> 理想方案是"SoC 深睡 + 低功耗 MCU 检测到人再唤醒"，但本系统**安全岛尚未实现软唤醒**，进 STR 后只能重新上电/KL15 拉高唤醒，故现阶段纯二选一。

## 状态与接口（GuaCarPowerManager）
- `POWER_STATE_SENTRY_MODE_ENTER_PREPARE`(0)：进哨兵。
- `POWER_STATE_SENTRY_MODE_EXIT_POST`(3)：退哨兵。
- 其他状态直接 `future.complete()`；需清理/恢复则做完再 complete。
- SDK 连接成功后主动 `getPowerState()` 拉一次最新状态。

## 调试
```bash
adb shell cmd car_service apply-power-policy gua_policy_sentinel_enter
adb shell cmd car_service apply-power-policy gua_policy_sentinel_exit
# IVI 触发：adb shell cmd com.meloui.car.sentinel.ISentinelManager set_ready_status 1
# CP0 串口输入 work 退出哨兵
```
